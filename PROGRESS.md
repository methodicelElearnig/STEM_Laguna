## Architecture (important before adding a screen 3/Q2)
- `#app` is fixed at 1920×1080 and scaled via a `transform: scale()` in
  `script.js` (`scaleApp()`) to fit any real window size, centered with letterboxing.
  **`scaleApp()` also subtracts the dev-bar's height** from available viewport height
  so the canvas doesn't render underneath it — if you ever remove the dev bar, this
  still works fine (falls back to 0 height).
- **All CSS in this project uses raw px values against the 1920×1080 canvas**, not
  responsive units. Keep doing that for consistency.
- Every screen is a `<main class="screen" id="screen-X">` inside `#app`, each with
  its own `<img class="bg">`. `showScreen(id)` in `script.js` hides all `.screen`s
  except the target and moves focus to that screen's `h2[tabindex="-1"]` (for screen
  reader announcement on navigation).
- **Gotcha (hit repeatedly):** any element that gets shown/hidden via the `hidden`
  attribute but also has its own `display` CSS rule (e.g. `display: flex`) needs an
  explicit `.foo[hidden] { display: none; }` override — otherwise the class's
  `display` rule beats the browser's default `[hidden]{display:none}` and the
  "hidden" element stays visible. Already fixed for `.dialog-overlay`,
  `.feedback-panel`, `.btn-check`, `.nav-fwd`/`.nav-back`. Apply the same pattern to
  anything new.
- **Feedback panel icon/text order:** `.feedback-panel` uses
  `flex-direction: row-reverse` so the icon renders on the visual **left** and text
  on the **right** — this looks backwards vs. a naive RTL flex-row reading but it's
  deliberate and matches the user's reference screenshots exactly. Don't "fix" it.
- **`.btn-check` size is standardized across all screens** — see the dedicated
  memory note below. Never give a screen-specific `.btn-check--X` class its own
  `width`/`height`/font-size; only `top`/`left`/`bottom` should vary per screen.
- **Question screens only** get a darkening overlay: `<img class="bg-overlay"
  src="assets/opacity br.png">` right after `<img class="bg">`. It's a full-canvas
  1920×1080 RGBA PNG (semi-transparent gray) at `z-index: 1`, sitting above the
  background photo but below everything else. `.stage-card` has an explicit
  `z-index: 2` specifically so it stays above this overlay regardless of DOM-order
  stacking quirks (elements with no explicit `z-index` are NOT guaranteed to stay
  below a sibling that has `z-index: 1`, even if they come later in the DOM — that's
  why the explicit `2` was added rather than relying on source order). **Do not add
  this overlay to `#screen-intro`** — the user explicitly asked for questions only.
  If you add a screen 4+, give it the same `.bg` + `.bg-overlay` pair and make sure
  any full-bleed card/content container on that screen has `z-index: 2` (or higher)
  too, following this same pattern.

### Interaction model (accessible drag-and-drop)
Two full input paths, both driving the exact same state — **do not let them diverge**:
1. **Click-to-place / click-to-swap** (`onTrayPillClick`, `onCellClick`): click an
   item to "pick" it (`aria-pressed="true"`), click a destination to place/swap.
2. **Real HTML5 drag-and-drop** (`dragstart`/`dragover`/`drop` handlers on tray
   pills and cells): same moves (tray→empty cell, tray→filled cell = swap, cell→cell,
   cell→tray = return), routed through the same shared helpers
   (`moveSourceToEmptyCell`, `swapSourceWithCell`) that the click path uses.
- If a screenshot mid-drag looks broken (a ghost item overlapping a cell), that's
  just the browser's native drag-preview image following the cursor before drop —
  not a bug. Confirmed by testing: post-drop DOM state is always clean.

Known drag-and-drop gotchas already fixed here, worth knowing if you touch this code:
- `<img>` elements are natively draggable in browsers — left alone, a pill's icon
  can start a *second*, competing native drag alongside the button's custom one,
  producing a broken "ghost of everything" visual. Fixed by `icon.draggable = false`
  in JS plus `-webkit-user-drag: none; pointer-events: none;` in CSS on
  `.pill-icon`/`.pill-text`.
- `dragenter`/`dragleave` don't reliably pair up when the drop target has nested
  children (dragleave fires on whichever child element the mouse left, not
  necessarily the container) — a naive `if (e.target === container)` guard on
  `dragleave` will basically never fire, leaving the `.drag-over` highlight stuck
  forever. Fixed with an enter/leave depth counter (`trayDragDepth`) on the tray,
  plus a global `document.addEventListener('dragend', ...)` safety net that
  force-clears every highlight regardless of how the drag ended.

- All correct (on either attempt): `lockExercise()` — disables every cell and the

## Screen 3 — fill-in-the-blank dropdown, Q1ב (`#screen-q1b`)

  Fisher–Yates on 2 items (a coin-flip swap), re-randomized fresh every load —

- `.btn-check--q1b` / `.feedback-panel--q1b` / `.nav-fwd`/`.nav-back` — screen-scoped

## Screen 4 — chart dropdown fill-in-blank, Q2א (`#screen-q2a`)
A bar-chart-reading question: 4 inline `<select>` blanks (3 numeric + 1 trend word),
same mechanism as screen 3's `.fill-select` (native selects, shuffled options, 2-attempt
grading, reveal on final miss) — reuses `.fill-select`/`.q-fill` verbatim, just a
different data set. No new grading pattern here, only a new visual: the chart.

### The chart
- The bars + fish-pattern fill + gridlines + basket graphic are **one pre-rendered
  image** (`assets/Group 22.png`, 506×508px) — not built from CSS bars. Only the axis
  numbers, axis title, and year labels are live HTML/CSS overlaid on top.
- **The gridlines in that PNG are NOT evenly spaced** (~8.4% margin above the "500"
  line and below the "0" line) — a naive `justify-content: space-between` on 11 evenly
  spaced `<span>`s drifts further off with each row. Fixed by sampling the actual
  pixel rows of the gridlines (PowerShell `System.Drawing.Bitmap.GetPixel`, looking for
  the semi-transparent-black `(0,0,0,alpha≈56)` gridline stroke down a column that
  crosses all of them) and hardcoding each label's exact `top: X%` inline in
  `index.html`. If this image ever gets replaced, redo that pixel sampling — don't
  reuse the old percentages blind.
- `.q2a-yaxis-track` is a dedicated inner wrapper `<div>` around the 11 number
  `<span>`s specifically so the **whole column** can be nudged as one unit (via
  `transform: translateY(...)` on the track) without touching the 11 individually
  calibrated per-span percentages or squishing their spacing. Don't add `top`/`bottom`
  offsets on this element (that resizes the box the percentages are relative to and
  re-introduces drift) — only `transform: translate()`.
- `.q2a-chart-wrap` uses `direction: ltr` internally (numbers-then-image,
  years-left-to-right) even though the page is RTL, because a financial/scientific
  chart's time axis reads left-to-right regardless of page language — plain `flex-row`
  in an RTL container would mirror the whole chart backwards.
- Chart-vs-text column order in `.q2a-body` is controlled via CSS `order` (`order: 1`
  on `.q2a-fill`, `order: 2` on `.q2a-chart-wrap`), not DOM order — the chart is
  `aria-hidden="true"` (purely decorative, the real content is the text/dropdowns) so
  reordering it visually doesn't affect reading/tab order.
- `.q2a-chart-wrap` currently has `transform: translateY(-162px)` — heavily
  hand-tuned via DevTools by the user (started as a literal "move it up 300px" ask,
  which overshot past the card's top edge and got dialed back). If asked to reposition
  this again, expect another few rounds of exact-pixel iteration.
- No help button/dialog on this screen — the user explicitly said it isn't needed
  here (unlike screens 1a/1b which both have one).

that way because the row/correctness model differs (row index match, not
category-string match) and because screen 2's helpers are already tangled with its
own DOM ids.

### Layout
- `.q3-table` is a real `<table>`, **952px wide** (same width as `.sort-table` on
  screen 2, since it also sits alone at the "start" edge of a `justify-content:
  space-between` `.q-body` — a lone child there naturally renders flush to the RTL
  main-start, i.e. the right, same as `.sort-table` does), 2 columns × (1 header + 3
  body rows). **Column DOM order is fact-column-first, answer-column-second** — first
  DOM `<td>` renders visually rightmost in this RTL table, and the reference mockup
  has the photo/label column on the right, answers on the left, so DOM order had to
  match that, same logic as screen 2's deplete/renew column order.
- **`.q3-table tbody tr` needs an explicit `height: 150px` *and* `.q3-table td` needs
  its own explicit `height: 150px` too** — a `height: 100%` on the cell's child
  (the answer button) silently collapsed to its `min-height` fallback (44px) when only
  the `<tr>` had an explicit height. This is a real CSS quirk: a percentage height on
  a table cell's child only resolves reliably when the **cell itself** also has an
  explicit height, not just the row — row height alone isn't treated as "definite" for
  that purpose in all cases. Hit this exact bug once already (see screen 2's identical
  `<tr>`-height note below) — this time it was bad enough to be visibly wrong (a
  ~22px-tall drop target instead of filling the ~150px row), so don't drop either
  height declaration if this table is resized again.
- `.q3-tray` is a single-column flex list (`540px` wide, matching the leftover space
  next to the 952px table, same math as screen 2's tray) holding the 3 unplaced
  answer cards; `margin-top: 64px` nudges it down to align with the table's first
  body row (below the header row).
- `.q3-answer` (the empty/filled table cell button) deliberately mirrors `.cell`'s
  *flat* look — no border/radius/shadow of its own, just a `background` tint via
  `[data-item]` when filled. An earlier version gave it its own chip-style
  border/radius/shadow at all times, which made **empty** cells show a stray pill
  outline that didn't match screen 2's blank-cell look — the user flagged this
  explicitly ("needs to look the same way ... as q1a"). Don't reintroduce always-on
  chip styling here.
- **Polaroid photos bleed past the row/column divider lines on purpose** (`150×120px`,
  25% bigger than the original `120×96px`, per explicit user request, with alternating
  `rotate(-3deg)`/`rotate(3deg)` tilt) — matches the reference mockup where each photo
  overlaps its row line slightly. This requires `.q3-fact-cell { overflow: visible; }`
  (overriding the base `.q3-table td { overflow: hidden; }`) **plus** promoting each
  `.q3-fact-cell` to `position: relative` with a **tiered `z-index` (top row highest,
  descending row by row)**. Without the z-index tiering, the bleed gets silently
  clipped by whichever sibling cell paints later in DOM order (the row below, or the
  answer column in the same row) — table cells otherwise paint in plain DOM order with
  no way for an earlier cell's overflow to show above a later one. This was a real bug
  the user caught via screenshot (a hard rectangular clip on the photo's top-left) —
  if these photos are resized/repositioned again, keep both the `overflow: visible`
  *and* the z-index tiering, not just one.

  (`revealAnswer`-equivalent, empties the tray), marks everything correct/green, shows
  the reveal-style "לא נורא!" panel. Feedback text/icon reuse the exact q1b/q2a/q2b

- No help button/dialog on this screen (matches q2a/q2b, not q1a/q1b).

## Screen 7 — fact vs. opinion sort, Q4 (`#screen-q4`)
Two open-ended drop-zone columns (`דעות או הרגשות` "opinions/feelings" left,
`עובדות מדידות` "facts/measurements" right — DOM order is facts-first/feelings-second
for the same RTL-first-child-renders-rightmost reason documented for screen 6's
table) that the learner sorts 9 statement cards into. Unlike every earlier sorting
screen, there's no fixed slot grid — each column is an open `<ul>` the student can
drop any number of cards into, and cards are revealed **one at a time** (not all at
once in a tray) via a single floating "current item" card (`#q4-current` /
`#q4-current-item`) that gets replaced by the next queued item every time the
current one is placed. This "reveal one at a time" behavior was an explicit user
request, inferred from a mockup screenshot that showed only one card near the check
button with both columns still empty.

### Layout
- `.stage-card`'s background image and **base height (848px → 983px)** were changed
  for this screen via live user DevTools edits, but `.stage-card` is the *shared*
  rule every screen uses — the height bump therefore also affects Q1א/Q1ב/Q2א/Q2ב/Q3,
  not just Q4. `#screen-q4 .stage-card` has its own `background-image` override
  (`assets/q4 blob main.png` instead of the shared `assets/blob-card.png`), added
  specifically because the user asked to swap only the background art, not the size.
- `.q4-col` height (615px) and `.q4-current`'s `top`/`left` position were also
  hand-tuned via several rounds of live DevTools edits mirrored back here — if a
  future resize of the card/columns makes the current-item card or the check button
  overlap the columns again, re-check these three numbers together, not just one.
- **The current-item card and the answer chips are two different visual styles on
  purpose.** The floating current-item card originally reused `q4 blob main.png`
  (a big bordered/shadowed card asset) but the user reverted that — it now stays the
  small plain teal pill (`.q4-blob`, `border-radius: 999px`, no image), and instead
  the *whole stage-card* background became `q4 blob main.png`. Don't re-merge these
  two — they were deliberately un-merged.
- The teal pill shape (`.q4-blob`) intentionally does **not** use the source
  `assets/q4 blob1.png` / `q4 blob2.png` — those speech-bubble PNGs have a pointer/tail
  at the bottom the user explicitly didn't want ("without the sharp thing at the
  bottom"). The pill is pure CSS (flat teal fill + `border-radius`), not a background
  image.
- Each placed answer chip shows a **circular ✓/✕ badge** after checking, reusing the
  exact same look as Q2ב's single-choice `.q-radio` (`.q4-blob-radio`, a plain CSS
  circle with `::after { content: "\2713" / "\2715" }`) — the user explicitly asked
  to reuse *that* pattern, not the initially-tried `gp-icon-correct/incorrect.svg`
  image icons (those are unused again now, see the asset list below). **Gotcha hit
  here**: `.q4-blob-radio { display: flex }` and the browser's UA `[hidden] {
  display: none }` rule have *equal specificity*, so the later author rule silently
  won and the badge stayed visible even while `hidden` was set — fixed with an
  explicit `.q4-blob-radio[hidden] { display: none; }` override. Worth remembering
  for any other element that sets its own `display` and also needs to support
  `hidden`.

### Interaction model
- Two ways to place a card, both routed through the same state: **(1)** drag the
  current-item card onto a column, or click a column while a current item exists
  (`q4PlaceCurrent`); **(2)** once placed, a chip can be **dragged directly from one
  column to the other** (`q4MoveToColumn`) — added per explicit user request ("I want
  to add the option to move them from one side to another") — or clicked to send it
  back to the queue (`q4ReturnToQueue`), where it becomes the current item again.
- **No `<img>` in this project should ever be natively draggable** — hit a real bug
  here where dragging for real (mouse, not automated) on the top-level `index.html`
  (but *not* inside `index_dev.html`'s iframe) would hang the whole tab, requiring a
  reload. Root cause: every screen's full-viewport `.bg`/`.bg-overlay` `<img>` is
  draggable by browser default, and a real drag gesture over one can start a second,
  competing native drag; at top level (not iframe-sandboxed) Chrome can try to drag
  the local file out of the tab and hang. Fixed globally — `img { -webkit-user-drag:
  none; user-select: none; }` near the top of `styles.css` — not just for this
  screen. If a future screen's drag interaction seems to "freeze the whole page"
  specifically outside the dev iframe, check this rule is still there before
  anything else.
- **Per-item locking, not screen-wide locking, on a wrong attempt.** Every earlier
  sorting screen (`q1Locked`/`q3Locked`) locks the *entire* interaction on the final
  wrong attempt only. Q4 is different by explicit user request: on **every** check
  (including the first, non-final attempt), whichever chips are already in their
  correct column lock in place individually (`q4LockedItems[id] = true`, disables
  that one chip, `draggable = false`) and turn green permanently, while the
  still-wrong chips stay open, draggable, and clickable so the student can fix just
  those. `q4ClearFeedback`, `q4ReturnToQueue`, and `q4MoveToColumn` all check
  `q4LockedItems` before touching an item.
- The shared "try again" / "correct" `.feedback-panel` is **not** fixed to one side.
  It's nested into whichever column currently has *fewer* placed items (more visual
  empty room) via `q4PlaceFeedbackPanel()`, called right before the panel is shown
  (both on a normal check and again after the final-attempt reveal, since that
  reassigns `q4Placed` to the answer key and the "smaller" column can change).
  Explicit user request, twice — first version hardcoded it into the feelings/left
  column, which was wrong for the general case; second pass made it dynamic. Panel
  width was hand-tuned to `500px`, centered via `left: 50%; transform:
  translateX(-50%);` inside whichever `.q4-col` it's moved into (`.q4-col` needs
  `position: relative` for that to anchor correctly).
- **9 statement texts were transcribed by the assistant from a screenshot**, not
  pasted by the user (`Q4_ITEMS` in `script.js`) — never independently verified
  against a source document. If anything about this question's content looks
  off (typo, awkward phrasing), that's the most likely place, not a code bug.
- Queue order (`q4Queue`) is **shuffled** (`q4Shuffle`, Fisher–Yates) on load rather
  than following `Q4_ITEMS` array order — the array happens to list all 4
  feelings-column items before all 5 facts-column items, which without shuffling
  made every playthrough reveal all of one side's answers before any of the other's.

## Shared helpers added this pass (script.js, near the top, after `showScreen`)
Three reusable functions/patterns now back several screens each — check these before
building a new screen that looks like it needs the same shape of logic, rather than
copy-pasting a whole new implementation:

- **`setFillBadge(select, ok)` / `clearFillBadge(select)`** — the ✓/✕ badge next to a
  `.fill-select` dropdown. Every dropdown-fill screen (Q1ב, Q2א, Q5) wraps each
  `<select>` in `<span class="fill-select-wrap"><select>...</select><span
  class="fill-badge"></span></span>`; these two helpers toggle `.correct`/`.wrong` on
  the **wrapper** (not the select) and set the badge's glyph, called alongside the
  existing `select.classList.toggle("correct"/"wrong", ...)` in each screen's own
  check-handler. Retrofitted onto Q1ב/Q2א after being built fresh for Q5 — the user
  asked for the badge to appear everywhere dropdowns are used, not just the new screen.
- **Correct-answer locking on retry, for dropdowns too.** All three dropdown screens
  (Q1ב/Q2א/Q5) now disable an individually-correct `<select>` the moment a first
  attempt is checked (only the still-wrong ones stay open for the second attempt) —
  matching the drag-and-drop screens' existing per-item-lock behavior (Q4, see above).
  This wasn't the original dropdown behavior (all selects stayed editable between
  attempts) — the user explicitly asked to bring it in line with the other question
  types. Each screen's own `xClearResult()` was also updated to skip `disabled`
  selects when clearing stale correct/wrong styling, otherwise changing one blank
  would visually un-mark an already-locked correct one.
- **`initVideoScreen(screen, continueBtnId)`** — full custom video-controls-bar
  engine (play/pause, seek, time, CC toggle, mute/volume, fullscreen), ported from
  the `video-controls-bar.md` reference pattern in the `stem-lomda-patterns` skill.
  Called once per video placeholder screen; forward nav on that screen starts
  `disabled` and flips to enabled on the video's native `ended` event. Captions are
  wired (`.vcap-src`/`[data-t]` spans, `data-end`) but empty on every placeholder so
  far — fill them in once a real clip + timing exists.
- **`initSingleChoice(prefix, nextScreenId, opts)`** — the Q2ב single-choice engine,
  generalized so Q7א/Q7ב could reuse it instead of duplicating ~90 lines each. `opts`
  lets a screen diverge from Q2ב's exact wording without touching the shared function:
  `correctPrefix` (default `"מצוין!"`), `wrongPrefix`/`wrongSuffix` (wrap each
  distractor's own `data-feedback` in a heading/closing line instead of showing it
  bare), `firstWrongText` (a generic first-attempt nudge, e.g. Q7ב's
  `"זאת טעות, נסו שוב."`, shown instead of the detailed per-distractor text — the
  detailed text then only appears starting on the **final** attempt), and
  `revealOnExhausted` (default `true`, matches Q2ב/Q7א: force-reveal + mark the
  correct option once attempts run out. Q7ב sets this `false` — on the final wrong
  attempt it still marks the correct option `.correct` **and** shows the *last-picked
  wrong option's own* detailed feedback, rather than switching to a generic "here's
  the answer" panel). Q2ב itself was **not** refactored onto this helper (left
  working as-is) — only new screens use it.
- **Shared image-zoom modal** (`#img-zoom-overlay`/`#img-zoom-full`/`#img-zoom-close`,
  one instance at the end of `index.html`, outside any `.screen`). Any button anywhere
  gets zoom-on-click by adding `data-zoom-src="path/to/full-image.png"` (and optionally
  `data-zoom-alt="..."`) — a single `setupImageZoom()` IIFE at the bottom of
  `script.js` wires every such button on page load via `document.querySelectorAll`, no
  per-screen registration needed. First used by Q5's two gallery images.

## The "shared position, colliding default" pattern — worth knowing before adding a screen
Nearly every `.btn-check` in the project has converged on the **same** screen-scoped
position: `top: auto; left: 167px; bottom: 180px;` (started as Q1ב's tuned position,
now reused verbatim by `.btn-check--q1a/q1b/q2a/q2b/q3/q5/q6/q7a/q7b`) — **Q4 is the
only screen still on the unscoped default** (`top: 962px; left: 7px`, from the base
`.btn-check` rule). If you add a new question screen's check button, start from
`left:167px; bottom:180px` as the default expectation, not the base rule.

Separately, the shared `.feedback-panel`'s own default position (`left: 182px;
bottom: 309px`) has landed on top of a screen's own content **three separate times**
(Q4's sort columns, Q5's image gallery, Q6's answer table) as new layout was added —
each time fixed with a screen-scoped `.feedback-panel--X` override placed in the
first genuinely empty space, found by measuring real element rects (Playwright
`getBoundingClientRect()` at design resolution, viewport `1920×1200` so `scaleApp()`
doesn't shrink anything) rather than guessing from a screenshot. If a future screen's
feedback panel looks like it's covering something, this is almost certainly why —
check for overlap with the same measurement approach before hand-picking new
coordinates.

## Interstitial transition cards (`#screen-q5-intro`, `#screen-q8-intro`)
Two plain "book + parchment card + המשך button" screens, reusing `screen-intro`'s own
markup verbatim (`.intro-stage` + `.book` + `.card`/`.card-line` + `.btn-continue` —
no new structural classes, no help button, no back button, matching `screen-intro`'s
own shape). Each needed a **screen-specific modifier class** (`.card--q5-intro` /
`.card--q8-intro`) rather than sharing one generic "centered" class, both because the
user wants to be able to tune each screen's text size independently going forward,
and because of a real bug hit while building these:

- **`.card-line:last-of-type` is shared with `screen-intro`.** `screen-intro` has 3
  `<p class="card-line">`s; its **last** one also matches `:last-of-type`, and so does
  the single short paragraph on `screen-q5-intro`/`screen-q8-intro` (a lone paragraph
  is trivially both first-of-type and last-of-type). Any edit to the shared
  `.card-line:last-of-type` rule therefore silently reaches into `screen-intro` too.
  This actually happened: a DevTools tweak intended for one of the transition cards
  (bumped to `font-size: 44px; margin-bottom: 118px`) pushed `screen-intro`'s third
  line down far enough to overlap its own "המשך" button and overflow the card — caught
  by screenshot, reverted. **Fix pattern**: give each transition card's own modifier
  class an explicit `:last-of-type` override too (`.card--q5-intro .card-line,
  .card--q5-intro .card-line:last-of-type { ... }`) so it wins on specificity
  regardless of source order, instead of touching the shared base rule. Keep
  `.card-line:last-of-type` itself at its original values (`font-weight: 500;
  font-size: 30px; margin-bottom: 0;`) — that's `screen-intro`'s own tuning, not a
  shared default to build on.
- `.card--q5-intro`/`.card--q8-intro` both set `justify-content: center` on the card
  (vs. `screen-intro`'s default top-packed flex column) since a one- or two-line
  message looked stranded near the top of the full-height card otherwise — reach for
  this same modifier shape (`justify-content:center` + its own `:last-of-type`
  override) for any future short interstitial.
- Both currently render their text as **exactly two lines via an explicit `<br>`** in
  the HTML, not by relying on `max-width` to force a wrap — more predictable than
  trusting the browser's line-breaking at a specific font-size/width combination, and
  is what the user asked for on `screen-q5-intro` specifically ("only in 2 lines").

## Scoring system + Screen 16 — completion screen (`#screen-ending`)
**Screens 1-7 are graded, screen 8 (q8a/q8b) is not** — q8a is an explicitly-confirmed
open-reflection drag-and-drop with no correct/incorrect mapping (see its own section
above and the persisted project memory), so it never calls `recordScore` and
contributes nothing to the final grade.

**Scoring infra** lives near the top of `script.js`, right after `setFillBadge`/
`clearFillBadge` (both of which several graded screens also call), since it needs to
be in scope for every screen's IIFE below it:
```js
var SCORE_WEIGHT = { q1: 0.5, q1b: 0.5, q2a: 0.5, q2b: 0.5, q3: 1, q4: 1, q5: 1, q6: 1, q7a: 0.5, q7b: 0.5 };
var TOTAL_QUESTIONS = 7; // logical questions (1-7), not screens
var questionScores = {};
function recordScore(key, fraction) { questionScores[key] = fraction; }
function computeFinalScorePercent() { /* weighted average -> Math.round(...*100) */ }
```
The three split questions (1/1ב, 2א/2ב, 7א/7ב — same split-question pairs the
progress-dot numbering already groups under one number, see the top of this file)
each carry **half weight per screen** so the pair together counts as one full
question, per the equal-weighted-scoring convention in `stem-lomda-patterns` →
`scoring-and-completion.md`. Every other graded screen (3, 4, 5, 6) carries full
weight 1. `TOTAL_QUESTIONS = 7` is the denominator (7 logical questions, not the 10
graded screens) — if a screen is ever added or removed from the SCORE_WEIGHT map,
this constant must be updated to match, or the percentage silently skews.

**`recordScore(key, fraction)` is called once per screen, at the exact moment that
screen's own exercise locks in its final result** — never re-derived later from a
post-reveal board (the reveal-the-correct-answer branch that runs when attempts are
exhausted overwrites the learner's own placement/selections for *display*, so the
correctness snapshot must be captured *before* that overwrite runs, not after):
- **Single-answer screens** (`q2b`, and `q7a`/`q7b` via the shared `initSingleChoice`
  helper — one shared hook covers both, per the "find the minimal set of shared
  insertion points" advice in the skill reference) record a plain `1` or `0`.
- **Multi-item screens** (`q1`/`q3`/`q6`'s drag-and-drop cells, `q1b`/`q2a`/`q5`'s
  fill-in-blank `<select>`s, `q4`'s two-column sort) record **partial credit**:
  `correctCount / totalCount` at the point of the final (possibly exhausted-attempts)
  check, captured via `cells.filter(c => c.classList.contains("correct")).length`
  (or the equivalent for `q4`'s `q4Placed` dict, which has no cell elements to query
  and instead tallies `q4CorrectCount`/`q4TotalCount` inline in its own existing
  correctness-computation loop) — added as one extra `var ...CorrectCount = ...`
  line right after each screen's existing correctness loop, then called from both
  terminal branches (all-correct → record `1`; attempts-exhausted → record the
  fraction).
  **The retry branch (attempts remain) never calls `recordScore`** — only the two
  terminal branches (solved, or exhausted) do, since the learner hasn't finished that
  screen yet on a mid-retry state.
- Verified end-to-end with Playwright: answered q7א+q7ב correctly (→ 14% = 1/7 of the
  grade, exactly), then answered q2ב wrong (score unchanged at 14%, confirming a wrong
  screen contributes 0 and doesn't need an explicit "record 0" call anywhere it isn't
  already present) — see script's own inline test notes if this needs re-verifying.

establishing shot). `.ending-panel` is `assets/small blob ending.png` (a small,
fully-closed rounded rectangle with a chat-bubble-style tail notch at the bottom-right

**Bug fixed post-ship**: the close button was only clickable on the sliver of itself
that pokes outside the card (the negative-offset region) — the rest of its 64×64 box

## Testing approach used throughout this project
No test framework in the project. Verification is ad hoc via Playwright, run against
a static file server:
- **Server**: `npx http-server -p <port> -s` from the project root (not `npx serve` —
  switched this pass). Always `cd` into the actual project directory first, or point
  http-server at it explicitly — running from the wrong cwd serves the wrong tree and
  every route 404s silently (looks like the server started fine).
- **Chromium**: don't reinstall Playwright's browser every time — it's already cached
  at `C:\Users\user\AppData\Local\ms-playwright` (confirmed present this pass);
  `npm install playwright` in a scratch folder is enough to get the JS package without
  re-downloading the browser binary.
- **Port hygiene**: pick a fresh high port per test run rather than reusing one —
  killing a background `http-server` process doesn't always free the port
  immediately, and a stale server still bound to an old port serves stale (or wrong)
  content while looking like it "just isn't responding" to a new request. Find the
  PID holding a port via `netstat -ano | grep <port> | grep LISTENING`, kill via
  PowerShell `Stop-Process -Id <pid> -Force`. Chromium also refuses to navigate to
  several "unsafe" ports (5060, 5061, etc. — SIP-related) — stay in the 8000+ range.
- **Jumping to a screen**: every screen is reachable via the in-page dev bar without
  playing through the whole flow — `page.fill('#dev-scr', String(n))` then
  `page.dispatchEvent('#dev-scr', 'change')`, where `n` is the screen's 1-based
  position in `document.querySelectorAll('.screen')` (fetch that list once per test
  run rather than hardcoding an index — it shifts every time a screen is inserted).
- **Testing a `disabled` element's real position/size**: `getBoundingClientRect()` on
  a `hidden` or not-yet-visible element returns all zeros. To measure a check
  button's actual CSS position before it would normally show, force `el.hidden =
  false` inside `page.evaluate()` first, measure, done — no need to actually play
  through the interaction that would reveal it.
- **Simulating drag-and-drop**: Playwright has no native HTML5 drag-and-drop support.
  To test a `drop` handler's guard logic (e.g. "does this reject a drop onto a locked
  cell"), construct a real `DataTransfer` inside `page.evaluate()`, `setData`, then
  dispatch synthetic `dragover`/`drop` events with `Object.defineProperty(evt,
  'dataTransfer', { value: dt })` (the `dataTransfer` property can't be set directly
  on a plain `Event`) — this exercises the actual handler code, not a mock.
  **Caveat learned on Q8א**: this synthetic approach dispatches straight into the
  handler and bypasses the browser's own native-drag eligibility checks entirely —
  it will report a false positive even when a real user's mouse-driven drag can't
  start at all (e.g. this project's global `img { -webkit-user-drag: none; }` rule
  silently blocking `draggable="true"` on a raw `<img>`). Use it freely for state/
  guard-logic checks, but verify at least once per new native-HTML5-drag screen with
  a genuine `page.mouse.move()` → `mouse.down()` → `mouse.move(..., {steps: N})` →
  `mouse.up()` sequence over real element bounding boxes — that's the only way to
  catch a drag source that silently can't be picked up by a real user.
- Always clean up afterward (stop the server process); scratch test scripts and
  screenshots live in the session's scratchpad directory, not the project folder.

- **Video behavior fixes** (all in `initVideoScreen()`, shared by all 5 video
  screens, so every fix applies everywhere at once):
  - The big center play button (`.video-play`) no longer reappears when a clip ends
    (it used to, letting you "replay" from the overlay button — that's now only
    possible via the in-bar play/pause toggle).
  - `showScreen()` now pauses the *previous* screen's `<video>` if it was still
    playing when you navigate away — previously audio kept playing after navigating
    to the next screen.
  - The custom control bar (`.vctrls`) auto-fades after 2s of no pointer movement
    **during playback only** (new `.vctrls-idle` class, opacity+pointer-events,
    separate from the pre-existing `.hidden`/`display:none`). It reappears instantly
    on mouse movement or on pause/ended, and it never force-hides on `ended` anymore
    (previously it did — the seek bar now stays visible after a clip finishes, since
    there's no other way to interact with it at that point).
    **Gotcha hit and fixed**: the idle-fade originally skipped hiding whenever
    `document.activeElement` was inside `.vctrls`, intended to protect a keyboard user
    tabbed onto the seek slider — but a plain **mouse click** on a `<button>` also
    leaves it focused, and since the overlay play button no longer reappears after
    `ended`, every replay necessarily happens via the in-bar button, which was
    permanently pinning the bar open on every replay. Fixed by checking
    `:focus-visible` instead of plain focus — keyboard tabbing still keeps the bar
    open, a mouse click no longer does.

- **Dev bar now syncs itself to real in-course navigation.** Previously `#dev-scr`'s
  number only updated when *using the dev bar's own* prev/next/number-input controls
  — clicking through the actual course (Continue/Back buttons, dropdown "next
  question" flows, etc.) left it stale, since those all call `showScreen()` directly
  without touching the dev bar. Fixed with a `syncDevBar` hook: `showScreen()` now
  calls it (if set) after every navigation, and the dev-bar IIFE assigns it to a
  closure that looks up the new screen's 1-based index in `devScreens` and updates
  `#dev-scr` accordingly. Any future navigation path that calls `showScreen()`
  automatically stays in sync — no per-screen wiring needed.
- **URL hash now updates on every screen change** (`history.replaceState(null, '',
  '#' + id)` inside `showScreen()`) — added when investigating why the client's
  external QA/annotation platform ("Metodika QA") wasn't detecting distinct "pages."
  This alone did **not** fix that platform's detection.
- **`data-screen="N"` attribute added to every one of the 20 `<main class="screen">`
  elements**, numbered 1–20 in DOM order (hardcoded directly in the HTML, not
  injected via JS) — this was the actual fix for the QA-platform page-detection
  issue. The platform's own UI surfaced a note literally referencing a `[data-screen]`
  selector (visible in a DevTools element-picker screenshot the user shared) as what
  its automatic page-scanner looks for; our markup had no such attribute at all
  (only `id="screen-X"`), which is why it detected zero pages. **Important:** this
  scanner appears to read the *uploaded static HTML*, not a live JS-rendered DOM —
  that's why the attribute had to be baked into `index.html` source rather than set
  at runtime in `script.js` (where it would've been invisible to a static scanner).
  If a screen is ever added/removed/reordered again, renumber every `data-screen`
  value to stay sequential and gapless — the platform's numbering (its own "20" /
  "(1…23)"-style counters) tracks this exactly. **Unresolved**: the platform's own
  help text also mentioned that comments on elements living in a popup or an
  "external message layer" (i.e. appended outside their triggering screen's DOM
  subtree — several of this project's own feedback panels/popups get moved to a
  different parent via JS, e.g. `q4PlaceFeedbackPanel()`) may still fail to map to a
  page even once base detection works. Not yet investigated further.
